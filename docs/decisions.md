# Журнал решений

| # | Решение | Альтернативы | Почему |
|---|---|---|---|
| 1 | Новый репозиторий | Достроить свой редактор Slidev | Старый проект решает другую задачу (визуальный редактор markdown) и принёс бы ~14 тыс. строк, не относящихся к PPTX/MP4/LLM |
| 2 | FastAPI + Python для API и воркеров | Node/TS везде | Лучшие библиотеки разбора .docx/.xlsx/.pptx; Pydantic задаёт и валидирует схему сценария |
| 3 | Vue 3 + TypeScript для интерфейса | React | Стек, которым владею лучше всего |
| 4 | Celery + Redis, две очереди (`ai`, `render`) | arq; очередь на Postgres | Жёсткие тайм-ауты (зависший Chrome), acks_late и повторы; LLM (I/O) и рендер (CPU) масштабируются отдельно |
| 5 | Postgres — источник правды о заданиях, Redis — только транспорт | Хранить статусы в result backend | История и прогресс переживают перезапуск Redis и проверяются на владельца как любые данные |
| 6 | Синхронный SQLAlchemy 2.0 + psycopg 3 | async SQLAlchemy | Один код моделей и сессий для API и воркеров Celery; нагрузка — единицы одновременных генераций |
| 7 | nginx — единственная точка входа, API на том же origin | Отдельный порт API + CORS | Cookie-сессии без CORS, лимит тела запроса на краю, заголовки безопасности в одном месте |
| 8 | Контейнеры: non-root, read-only FS, `cap_drop: ALL`, `no-new-privileges` | По умолчанию | Требование задания «контейнеры без прав root» и минимальные права на случай RCE через рендер |
| 9 | PPTX: слайд верстается в HTML/CSS, Chromium измеряет каждый элемент, python-pptx создаёт нативные объекты | Координатная вёрстка в python-pptx; PptxGenJS; слайды картинками (экспорт Slidev/Marp) | Переносы и подгонку текста делает браузер, превью — та же вёрстка; текст, таблицы и графики остаются редактируемыми. Графики PptxGenJS в Keynote пустые даже в минимальном примере, у python-pptx отображаются (проверено экспортом из Keynote) |
| 10 | Шкалы осей графика считаются один раз на стороне вёрстки и передаются в PPTX | Автомасштаб PowerPoint/Keynote | Иначе Keynote выбирает другой шаг сетки, и график в файле расходится с превью, которое пользователь утвердил |
| 11 | Цифры считает код по таблице и хранит как факты с ID; модель ссылается на факты и не пишет числа | Модель пишет числа сама; модель пишет, код сверяет | Исключает ошибки переписывания и арифметики; первоисточник — таблица, как требует заказчик. Ошибки интерпретации ловит шаг проверки сценария |
| 12 | Недостающие показатели — фиксированный набор операций над фактами (`sum`, `difference`, `ratio`, `percent_of`, `percent_change`, `share`, `scale`) | Python-код от модели в песочнице | Код от модели пришлось бы изолировать от секретов, сети и чужих файлов; операции над ID безопасны, воспроизводимы и понятны на шаге проверки |
| 13 | Сценарий ссылается на факты по именам, числа в текст попадают только через подстановки `{имя}` | Модель пишет готовый текст с цифрами | Каждую цифру на слайде можно проследить до ячейки Excel; выдуманное число не проходит проверку и возвращается модели с точной ошибкой |
| 14 | Модель выбирает тип слайда и наполнение, вёрстку делают наши шаблоны | Модель генерирует HTML слайдов | Нет исполняемого кода от модели, стабильное качество, новый тип слайда — один шаблон |
| 15 | Агент: один вызов модели пишет весь сценарий, расчёты объявлены в нём же; наш код проверяет и возвращает ошибки (до 3 попыток) | Вызов функций (tool calling) по шагам; JSON-режим сервера | Меньше обращений к модели — быстрее; работает на любом OpenAI-совместимом сервере: в карточке Qwen3.8-27B вызов функций и структурированный вывод не описаны |
| 16 | Модель для теста — `qwen/qwen3.8-27b` через OpenRouter, рассуждения выключены (`LLM_EXTRA_BODY`) | Более крупные модели OpenRouter | Та же модель, что в контуре заказчика: качество и скорость на тесте отражают прод. Параметр отключения рассуждений у OpenRouter и vLLM разный — он вынесен в настройки |
